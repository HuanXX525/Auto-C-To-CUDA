# M8-A2 instance 10 数值分叉复查（2026-10-11）

本记录补充已冻结的 `m8_a2_uniform.json` 回执，不修改原始回执、CPU 基线或 GPU 物理/传感器算法。场景为 uniform long-noise、空故障、instance 10、seed 12515、`dt=0.01 s`、12000 步。

## 定位结果

报文 seq 979 的 seeker 样本来自 `t=9.7699999999998361 s`：配置有 `0.02 s` 延迟，不能用报文时间 `t≈9.79 s` 反推该次真值。该时刻 CPU/GPU 的随机数状态完全一致；量化前差异来自 LOS-rate 真值，而非随机数抽样顺序或噪声幅度。

| 量（GPU − CPU） | 测得差异 |
| --- | ---: |
| 导弹 ECEF `x` | `+4.656612873077393e-10 m`，此量级的一个 double ULP |
| 相对位置 `r.x` | `-4.656612873077393e-10 m` |
| 弹目距离 | `+4.4711256919072184e-10 m`，CPU 距离 `8.0044212130134493 m` |
| `(r × v).z` | `-9.940267775565559e-08 m²/s` |
| LOS-rate 真值 `.z` | `-1.5502714788978578e-09 rad/s` |
| 随机游走状态 | `+5.293955920339377e-23 rad/s` |
| 量化前测量值 | `-1.5502714788978578e-09 rad/s` |
| 量化前值除以 `1e-7` | `-0.015502714784815907` 档 |

原始导弹 `x` 为 CPU `-2770259.7625481389 m`、GPU `-2770259.7625481384 m`。目标状态在该次探针中相同。`LOS-rate.z` 的实现是 `((r × v).z) * (1 / |r|²)`；仅 `r.x` 的一个 ULP 乘以约 `213.4689 m/s` 的相对 `v.y`，就贡献约 `-9.94042e-08 m²/s`，解释了几乎全部叉积差异。相对速度还有 `1e-11 m/s` 量级差异。

CPU/GPU 的 seeker RNG 状态在该次调用前均为 `349212110524217457`，调用后均为 `2179902808902809211`。CPU 白噪声为 `3.472421200518633e-05`；GPU 从量化前值减去真值和随机游走反推约为 `3.4724212005185842e-05`。随机游走分别为 `-1.5076784004257732e-07` / `-1.5076784004257727e-07`。两侧的量化前值分别为 `-0.010528448895384356`、`-0.010528450445655835`，跨越同一半档边界，最终形成 `-0.0105284` / `-0.0105285`。其后飞控在 seq 980～11999 保持各自的 seq 979 指令，末端水平位置相差 `1.5593378286782649 m`。

初始状态在高精度探针中一致；前 0.21 秒连续采样时，首次观测到的导弹状态差异是 `t=0.06 s` 的 `vz` 末位（约 `5.55e-17 m/s`）。即使状态输入一致，`t=0.01 s` 的叉积结果也已有一个浮点末位差异。以上证据支持跨 CPU/GPU 浮点舍入及长期累积在近距离几何中被放大；没有发现 RNG 错位、样本延迟错位或 seeker 公式不一致。它未定位到单条硬件指令，也不证明所有物理模块逐位等价。

## 验证与处理

- CPU 基线仍使用 Aircraft-Simu `970bdfb`，通过单独编译的临时包装器记录真值和噪声；GPU 临时探针只记录输入与中间值。两侧探针运行的 `sensor_log.bin` 与原 M8-A2 结果逐字节一致。
- 探针源码已从 `converted/environment/sensor_noise.cu` 和 `sensor_seeker.cu` 撤回。恢复后的 GPU 再次运行，`sensor_log.bin`、`command_log.bin`、`trajectory.csv`、`trajectory_diagnostics.csv` 和 `event_log.txt` 与原 M8-A2 单实例结果逐字节一致。
- 保留现有仅适用于冻结输入和一个实例的有符号校准；不调整 `round`、物理积分或 CPU 基线来匹配一个浮点末位。M8-A3 对其它实例仍使用默认容差，出现新的边界分叉时需独立诊断。
- 本地探针日志位于忽略的 `gpu_workspace/build/diagnostics/m8_seed12515_20261011/`。`cpu_early_probe.log` SHA-256 为 `2d78237a4af944d092dcb578f2db7694fc83cedf736be13c497590d623a29805`，`gpu_early_probe.log` 为 `386d1fb39db285b25c762f09670fa9e16162cfa07c80cee3be6e00f9458af069`。

## 回执与重新构建

原 M8-A2 回执保留当时的 GPU 二进制 SHA-256 `ee3b885e6bb4dd675aaaa299dd34a1fc005e4cb31e36599efa662a623900ec98`。当前 Makefile 未传入 NVCC 的 `--frandom-seed`；对相同源文件重复编译并链接观察到不同二进制 SHA（例如 `4ad9db1f…` 和 `2b5da610…`），而恢复后单实例输出仍逐字节一致。当前 `--check` 验证历史结果、输入与回执，明确报告当前检查器或二进制与历史记录的 SHA 不同；它不把重新构建的二进制冒充成回执中的原件。以后若需要逐字节可复现构建，可在新基线中给各 CUDA 源文件固定不同的 NVCC random seed，并重新做正确性验收。

# 方案三（批量 UDP，保留网络模块）可行性评估

- 日期：2026-08-20
- 范围：评估"保留双进程 UDP 网络架构、改为批量消息格式，env/fc 两侧各自迁移 GPU"（方案三）与
  方案二（去网络合并 + 单 kernel GPU）的改动量对比与风险分析。
- 前置阅读：[Aircraft_Simu_To_Merged_Sim.md](../去网络端口整体迁移/Aircraft_Simu_To_Merged_Sim.md)、
  [Gpu_Migration_Guide.md](../去网络端口整体迁移/Gpu_Migration_Guide.md)

---

## 0. 结论先行

**方案三的总改动量不会比方案二小，大概率更大。**

- 它确实避开了"去网络合并"这一步，但该步在方案二里只是小头（约 350 行）；
- GPU 迁移的硬核部分（状态收集、日志缓冲化、divergence 修复）方案三需要在 **env/fc 两侧各做一遍**；
- 还要新增批量协议、双进程锁步协调、独立 fc host 驱动等约 1000+ 行新代码；
- 方案二里 fc 侧迁移几乎免费（11 个模块纯计算、0 malloc/0 I/O，标 `__device__` 即用），
  方案三把它拆成独立进程后反而要为它单独写 host 驱动与日志回放，是净增的工作。

## 1. 方案三定义

```
environment_sim 进程（GPU，batch=N）           flight_control_sim 进程（GPU，batch=N）
┌──────────────────────────────────┐          ┌──────────────────────────────────┐
│ env kernel: 线程=实例             │          │ fc kernel: 线程=实例              │
│   build_sensor_frame (per iid)    │          │   flight_controller_step (per iid)│
│   D2H 批量传感器帧                │          │   D2H 批量控制指令                │
│   批量编码 → 单个/多个 UDP 数据报 ─┼─────────>│   批量解码 → H2D                  │
│   recvfrom 批量控制指令           │<─────────┼── sendto 批量控制指令            │
│   H2D 分发回各实例 → update_truth │          │   internal_log 缓冲回放           │
└──────────────────────────────────┘          └──────────────────────────────────┘
```

## 2. 原架构关键事实（评估依据）

| 事实 | 数值/位置 | 对方案三的意义 |
|---|---|---|
| SensorFrame 线格式 | 36（头）+ 196 = **232 B/包**（packet.h） | 256 实例批量 ≈ 58 KB，塞一个数据报勉强可行 |
| ControlCommand 线格式 | 36 + 156 = **192 B/包** | 同上；1024 实例 ≈ 232 KB，**必须多数据报或改 TCP** |
| 收包缓冲 | env/fc 两侧均 `PACKET_BUFFER_SIZE 1024`（env_app.c:45, fc_app.c:28） | 批量化必须加大，现缓冲装不下 2 个实例 |
| 实例终止语义 | env 命中 `hit` 即 break（env_app.c:3014-3018）；fc 靠 2s recvfrom 超时退出 | **批量锁步与"实例各自不同步结束"冲突，见 §4.1** |
| fc 主循环 | recvfrom → decode → step → 写日志 → sendto（fc_app.c:553-618） | 批量化需重构为"收整批 → 分发 → 计算 → 收集 → 发整批" |
| 通信延迟/乱序故障 | env 侧每实例独立状态（communication_delay_line） | 每实例状态在 GPU 上，**语义天然保留，无需额外改动** |
| 心跳/实例管理器 | 每实例发 ready 心跳（fc_app.c:543） | 批量版需改为按批发一次，tools/instance_manager 需批量化 |

## 4. 方案三独有风险

### 4.1 锁步终止语义冲突（最严重）

原架构每个实例独立运行：实例 A 第 5000 步 hit 后 env 停发、fc 超时退出；实例 B 可跑到第 12000 步。
批量锁步必须**跑到最后一个实例结束**，已结束实例要打 finished 标记并在两侧跳过步进，
否则会给已结束实例多写日志帧——直接破坏验收标准（event_log 逐字节一致、bin 日志大小一致）。
方案二（每线程独立 `while`）天然没有这个问题。

### 4.2 UDP 批量尺寸与数据报数

- 256 实例：传感器批 59.4 KB（一个数据报，回环可用；真实网卡 MTU 1500 需 40+ IP 分片，效率低）
- 1024 实例：237.6 KB → 必须分 4 个数据报或改 TCP 流
- 现收包缓冲 1024 B，必须加大

### 4.3 每步锁步开销

每步 = 2 次 kernel launch + 4 次 memcpy（D2H/H2D ×2）+ 2 次 UDP 往返。
256 实例粗算 ~0.4 ms/步 × 12002 步 ≈ **5 s，比方案二 1.95 s 慢约 2.5×**。
可选"多步打包"（K 步传感器帧一报、K 步指令一报）把往返降 K 倍，但改变延迟语义，
且与通信延迟故障注入的逐帧语义需要重新核对。

### 4.4 显存无收益

日志缓冲总量（sensor/command/internal/truth/diagnostics/events 5 条流）与方案二相同，
只是分摊到两个进程；4 GB 卡上总占用不减少。

### 4.5 调试与故障面扩大

跨进程批量锁步新增失败模式：数据报丢失（UDP 无保证）、乱序、部分实例提前结束、
超时契约重定义；方案二完全没有这些问题。

## 5. 方案三的真实优势（需承认）

1. **保留分布式架构/协议真实性**：端口、CRC、心跳、实例管理器语义原样保留；
   若未来目标是多机扩展或混合 CPU/GPU 部署，方案三是唯一衔接路径。
2. **增量验证容易**：可做 GPU env ↔ CPU fc（真 UDP 混合跑）或反之，
   两侧独立对照验证；方案二只能整体对比 CPU/GPU 输出，故障定位面更大。
3. **自动化层面确实避开了最难语义化的一步**："把两个主循环合并成一个"（方案二的核心，
   需理解 sendto/recvfrom 替换为直接调用、日志所有权转移）是语义变换；
   而"批量协议 + 双侧各自迁移"更模板化，更贴合现有 ROSE 工具链的机械变换风格。

## 6. 结论与建议

| 目标 | 建议 |
|---|---|
| 单纯"N 实例 GPU 加速" | 方案二已跑通（12/12 PASS），**维持方案二**，不建议为方案三投入 |
| 保留网络栈 / 支持未来多机或混合部署 | 方案三可行，但需接受 ~2× 工程量和 ~2.5× 锁步开销；可先做 §7 的中间里程碑验证价值 |
| 降低自动化难度 | 方案三"每步更模板化"的直觉成立，但总工作量（双侧迁移 + 协议 + 协调）仍超过方案二 |

### 6.1 推荐中间里程碑（低成本获取方案三的最大好处）

若真正看中的是方案三的**增量验证**能力，不必实现完整批量协议：
- **GPU env（单实例/小批量）↔ CPU fc（真 UDP）混合跑**，即可独立验证 env 侧 GPU 迁移
  的正确性（env 侧输出与 CPU 基线对照，fc 行为保持原样）；
- 反之亦然。该里程碑不需要批量协议、不需要 fc kernel、不需要终止语义改造，
  工程量约是方案三的 20%，可作为方案二开发过程中的一个验证环节。

## 7. 附：后续若要启动方案三的注意点

- 先定数据报策略：≤256 实例单数据报 / >256 多数据报 / TCP 流三选一，且需加大两侧收包缓冲；
- 批量协议需携带每实例 seq 与 finished 标志，两侧解码后按 instance_id 固定序分发（保确定性）；
- fc 进程新增独立 host 驱动，internal_log 沿用"设备缓冲 + host 回放"模板（92 字节记录，与 CPU 布局逐字节一致）；
- 心跳改为按批一次，instance_manager 增加批量启动模式；
- 参数化回归脚本需扩展为三进程编排（env-batch、fc-batch、CPU 参考）。
